## 7. Observaciones / Issues

### ⚠️ Issue 1 — FK e índice UNIQUE sin guarda de idempotencia en 018 y 019 — Medio

Mismo issue reportado en el PR anterior (scripts 014/015). Los `ALTER TABLE ADD CONSTRAINT` y `CREATE UNIQUE INDEX` están fuera de cualquier guarda. Si el script se re-ejecuta con la tabla ya existente, falla con "already exists".

**Corrección mínima:**
```sql
-- FK
IF NOT EXISTS (SELECT 1 FROM sys.foreign_keys 
               WHERE name = 'FK_SolicitudesFacturacion_Solicitudes_IdSolicitud'
                 AND parent_object_id = OBJECT_ID(N'[Core].[SolicitudesFacturacion]'))
BEGIN
    ALTER TABLE [Core].[SolicitudesFacturacion] WITH CHECK
        ADD CONSTRAINT [FK_SolicitudesFacturacion_Solicitudes_IdSolicitud]
        FOREIGN KEY ([IdSolicitud]) REFERENCES [Core].[Solicitudes] ([IdSolicitud]);
END
GO

-- UNIQUE index
IF NOT EXISTS (SELECT 1 FROM sys.indexes
               WHERE name = 'UQ_SolicitudesFacturacion_IdSolicitud'
                 AND object_id = OBJECT_ID(N'[Core].[SolicitudesFacturacion]'))
BEGIN
    CREATE UNIQUE NONCLUSTERED INDEX [UQ_SolicitudesFacturacion_IdSolicitud]
    ON [Core].[SolicitudesFacturacion] ([IdSolicitud] ASC) ...
END
GO
```
Mismo patrón para el FK/índice del script 019.

### ℹ️ Observación — US 34158: no tiene tabla propia, reutiliza `GestionFlujos.FlujosEntidadesTracking`

La emisión de aval no genera una tabla nueva; el evento queda registrado en el sistema de flujos existente y el nuevo SP solo provee una vía tipada para consultarlo por `OrigenEvento`. Es una decisión de diseño válida — evita proliferación de tablas de evento si el sistema de flujos ya cubre la necesidad. No hay observación de calidad, solo documentar la decisión.

### ℹ️ Observación — Patrón `_BySolicitud_Select` retorna `Existe BIT` (no el registro)

Tanto `SolicitudesFacturacion_BySolicitud_Select` como `SolicitudesPagoConfirmado_BySolicitud_Select` retornan únicamente `CAST(... AS BIT) AS Existe`, sin los datos del registro. Es suficiente para la lógica de habilitación/bloqueo que requieren las US, y evita exponer datos innecesarios. Si en el futuro se necesita mostrar `FechaSolicitud` o `FechaPagoConfirmado` en el front, habrá que agregar un SP `_ByIdDetalle_Select` o extender este.

## 8. Veredicto

**✅ Aprobado con observaciones menores.**

Los 3 scripts cubren la totalidad de los criterios de aceptación y reglas de negocio de las US 34156, 34157 y 34158. El patrón de tablas de evento con UNIQUE en `IdSolicitud` es correcto y enforcea a nivel DB las reglas de unicidad. Los SPs siguen el estándar Garantizar completo.

El único issue estructural es la falta de guardia de idempotencia en FKs e índices (igual que el PR anterior), que no afecta la primera ejecución pero sí re-ejecuciones del script.

**Recomendación:** Corregir Issue 1 (idempotencia de FK e índices) antes de mergear a main, alineando con el mismo fix pendiente de los scripts 014/015 del PR anterior.
